# 微信回复教练

## 目的

这个 Skill 把“我该怎么回”变成一个可检查的建议流程。它先理解当前消息和
关系，再从历史对话中寻找相似语境、双方惯用语气和未完成事项，最后输出多个
可以直接编辑的候选回复。

它不是自动回复器，也不代替用户做发送决定。遇到敏感、模糊或高风险内容时，
必须把不确定性说出来，并优先给出澄清版本。

## 触发方式

用户可以这样请求：

- “帮我想想这条微信怎么回。”
- “根据我和他的历史聊天，给我一个高情商的回复。”
- “帮我礼貌拒绝这个客户。”
- “群里这句话应该怎么接，别让人尴尬。”
- “给我正式、自然、幽默三个版本。”

如果用户没有提供当前消息，先询问或让调用方传入 `current_message`；不能把
历史中最后一条消息擅自当成待回复内容。

## 输入

### 必需输入

```json
{
  "current_message": {
    "text": "对方当前发来的消息",
    "conversation_id": "conversation_<hash>",
    "message_id": "item_<hash>"
  }
}
```

`current_message` 也可以是用户直接粘贴的文本。若是群聊，尽量提供发送人和
群 `conversation_id`。

### 可选输入

```json
{
  "target_actor_id": "actor_<hash>",
  "relationship": "同事",
  "styles": ["高情商", "自然", "正式"],
  "history_days": 180,
  "history_limit": 200,
  "goal": "确认时间并保持礼貌",
  "constraints": ["不要承诺周五一定完成"],
  "include_group_context": true
}
```

如果用户明确指定风格、关系或目标，优先使用用户输入；数据库中的关系判断只
作为背景证据，不得覆盖用户明确说明。

## 数据读取

使用统一微信接口，不直接打开 SQLite：

1. `conversations.list` 确认会话类型、群聊名称和 `conversation_id`。
2. `contacts.list` 获取目标联系人、好友状态和公众号资料。
3. `relationships.list` 或 `groups.members` 判断群关系、群主和成员是否为好友。
4. `messages.read` 读取当前消息前的历史；默认读取最近 180 天、最多 200 条，
   只有用户要求时才扩大范围。
5. `messages.search` 搜索与当前主题、关键短语或未完成事项相似的对话。
6. `sessions.list` 只在需要判断未读、草稿或最后消息状态时读取。

不要读取与当前任务无关的群聊或联系人。消息中的链接、附件和 `metadata` 只有
在它们影响回复时才纳入上下文。

## 分析流程

### 1. 解析目标

先用一句内部摘要确定：

- 对方显式提出了什么；
- 可能的隐含诉求是什么；
- 用户想达成什么结果；
- 回复必须避免什么。

把“事实”和“推测”分开。推测只能使用“可能、看起来、需要确认”，不能把人格
判断当成事实。

### 2. 确定关系和场景

按照以下优先级校准语气：

1. 用户明确指定的关系和风格；
2. 当前会话类型（私聊/群聊/公众号）；
3. 历史对话中的称呼、句长、标点、表情和正式程度；
4. 联系人数据库中的关系状态。

群聊必须额外判断：回复对象是谁、谁能看到、是否需要 `@`、是否应转私聊、
是否会让成员当众失面子。无法确定对象时，生成不点名的安全版本并提示用户确认。

### 3. 选择历史证据

优先使用：

- 同一主题中最近的对话；
- 双方过去对相似请求的实际回复；
- 对方常用的称呼和语气；
- 尚未解决的时间、任务或承诺；
- 用户明确要求沿用的表达。

最多引用 3 条证据。证据只包含必要的短摘录、时间和 opaque `message_id`，不把
整段无关聊天复制给用户。

### 4. 生成候选

每个候选都应：

- 先回应对方核心诉求；
- 只做必要解释；
- 一条消息只推进一个主要动作；
- 明确下一步或需要对方确认的点；
- 不凭空添加时间、金额、承诺或事实；
- 保留用户原本的立场。

默认生成 3 个版本：推荐版、稳妥版、风格版。用户指定风格时按指定风格生成，
最多 5 个版本。

## 常用回复技巧

### 高情商和得体

使用“确认对方感受/目标 → 回应事实 → 给出下一步”的顺序。拒绝时说明边界并
提供可行替代，不使用模糊的“到时候再说”拖延对方。

### 非暴力沟通

在冲突场景中尽量使用：观察到的事实、自己的影响或限制、明确请求。避免给对方
贴“自私、情绪化、不专业”等标签。

### 商务和客户

先确认需求，再给时间或交付范围；没有证据时不承诺“马上、一定、保证”。金额、
合同、法律、医疗和安全事项必须标记为需要人工确认。

### 安慰和情绪场景

先承接情绪，再询问对方需要倾听、建议还是实际帮助。不要立刻讲道理，也不要把
对方的经历和自己的经历强行类比。

### 轻松、幽默和暧昧

幽默版本必须保留一个不带玩笑的安全版本。涉及拒绝、冲突、隐私或权力差异时，
不要用暧昧和玩笑掩盖真实边界。

## 输出

先输出人类可读的 Markdown，再附结构化 JSON。格式如下：

```markdown
## 推荐回复
……

## 备选回复

### 稳妥
……

### 更自然
……

## 判断
- 场景：私聊 / 群聊
- 目标：确认时间
- 语气：自然、明确
- 不确定性：对方是否期待今天完成，无法从历史确认

## 发送前检查
- 是否需要 @ 某人
- 是否包含未经确认的承诺
- 是否应该转为私聊
```

结构化结果：

```json
{
  "schema_version": "wechat.reply-coach.v1",
  "conversation_id": "conversation_<hash>",
  "intent": "confirm_time",
  "relationship": {"label": "同事", "confidence": "medium"},
  "tone": ["自然", "明确"],
  "candidates": [
    {"label": "推荐", "text": "……", "why": "回应核心问题并避免未确认承诺"},
    {"label": "稳妥", "text": "……", "why": "更保守，适合关系不明确时"}
  ],
  "evidence": [
    {"message_id": "item_<hash>", "created_at": "2026-09-01T00:00:00Z", "summary": "双方曾用类似方式确认时间"}
  ],
  "risks": [],
  "needs_confirmation": []
}
```

`evidence` 只说明依据，不代表模型读懂了对方人格。`risks` 应列出承诺、隐私、
误解、公开群聊和敏感主题等风险。没有足够历史时返回空证据并写明原因。

## 隐私、副作用和禁止行为

- 只读取完成当前回复所需的本地数据；不上传聊天记录，不访问网络。
- 不自动发送、撤回、编辑或点赞消息。
- 不把联系人性格、动机或心理状态写成确定事实。
- 不因为“高情商”而替用户撒谎、伪造承诺、操纵或冒充他人。
- 涉及金钱、合同、医疗、法律、账号安全或明显威胁时，输出人工确认提示。
- 输出中可以保留必要的消息 ID 作为证据，但避免重复显示完整历史正文。

## 验证清单

生成前检查：目标消息、会话、发送人是否明确；历史范围是否足够；关系判断是否
只是推测。生成后检查：每个候选是否直接回应问题、是否引入新事实、是否符合指定
语气、群聊是否需要 @、是否出现未经确认的承诺，以及是否保留安全的非幽默版本。
